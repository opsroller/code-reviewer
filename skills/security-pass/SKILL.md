# Security pass

A reviewer's security pass on a change, not a full audit. Based on the
OWASP Code Review Guide v2 (preparation, threat context, risk-based
review, source-to-sink), the OWASP Top 10 (2025) and the OWASP Secure
Coding Practices. Use the project's security model from its review notes.

## 1. Set the context (2 minutes)

- What does this code protect? Which data is sensitive (credentials,
  personal data, payment data, save or user files, signing keys)?
- Where are the trust boundaries: network, files, user text, IPC, plugins
  or scripts calling in, third-party services?
- How exposed is it: public internet, logged-in users, local only,
  build-time only?

Rate the change **high** (exposed, handles sensitive data or auth),
**medium** or **low** risk. High risk: read every line twice, and ask for
a second reviewer with security expertise if you are not one.

## 2. Source to sink

For each new or changed input (source), follow it to every place it is
used (sink): a query, a shell command, a file path, a template or HTML
output, a deserializer, a log line, an allocation size, a redirect URL.
If nothing on the path validates, encodes or bounds it, you have a
finding. When you find one, search the change and nearby code for the
same pattern.

## 3. Checklist by control

| Control | Look for |
|---|---|
| Input validation | Validated at the trust boundary by allow-list (type, length, range, format); internal code may then assume valid input. Parsers bounded in size and depth. |
| Output encoding | Encoded for its sink (HTML, SQL, shell, path, log). Parameterized queries; no string-built commands. |
| Authentication | No new path that skips it; credentials never logged or hard-coded; secure defaults. |
| Authorization | Checked server-side on every path and every object (no ID guessing, no client-trusted roles). Least privilege for new permissions, tokens and file modes. |
| Session and tokens | Expiry, rotation, revocation; tokens not in URLs or logs. |
| Cryptography | Standard libraries and current algorithms only; no home-made crypto; keys from a secret store, not the repo; secure randomness for secrets. |
| Error handling | Errors handled, not swallowed; fail closed; no stack traces or internals to users; state consistent after failure (OWASP 2025 A10, mishandling of exceptional conditions). |
| Logging and alerting | Security-relevant events logged; no secrets or personal data beyond the project's policy; log injection prevented. |
| Configuration | No debug modes, open CORS, default passwords or permissive settings shipped; secure headers where web-facing. |
| Supply chain | New dependency justified, maintained, from a known source, version pinned, lockfile regenerated by tooling, license compatible with the project. Build scripts and CI changes reviewed like code (OWASP 2025 A03). |
| Memory safety | In unmanaged code: bounds, lifetimes, ownership, integer overflow in size calculations. |
| Secrets | None in code, config, tests, fixtures, history or logs. A leaked secret is 🔴 and must be rotated, not just deleted. |

OWASP Top 10 (2025) map, for naming findings: A01 Broken Access Control,
A02 Security Misconfiguration, A03 Software Supply Chain Failures, A04
Cryptographic Failures, A05 Injection, A06 Insecure Design, A07
Authentication Failures, A08 Software or Data Integrity Failures, A09
Security Logging and Alerting Failures, A10 Mishandling of Exceptional
Conditions.

## 4. Severity

- 🔴 **Blocking**: an exploitable path or a leaked secret, a missing auth
  check, an injection sink reachable from untrusted input.
- 🟡 **Should fix**: defence-in-depth gaps with no direct path today.
- 🟡 **(optional)**: hardening ideas.

Say which findings are demonstrated and which are hypothetical. Never post
exploit details for an unfixed hole in a public place; tell the author
directly and follow the project's security disclosure rule.

## 5. Contributions from outside

For PRs from outside the team: look for obfuscated code, unexpected
network calls, new install or build hooks, and changes to CI that run with
secrets. Do not run untrusted code with credentials available.

## Documentation this work owes

A security-relevant change owes **reference** for its security behaviour
(permissions, config keys, limits) and, if a trade-off was made, an
**explanation** of it. Ask the author for both in the same PR.

## Failure modes

- Checking only the diff, not where the new input ends up.
- Trusting client-side checks.
- "It's internal" without checking who can actually reach it.
- Treating a dependency bump as noise.
- Burying a 🔴 security finding among nits.
